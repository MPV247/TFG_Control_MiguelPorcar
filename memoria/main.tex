\chapter{Análisis}

\section{Requisitos}
Para dotar de rigor metodológico al proyecto, los requisitos se han dividido en funcionales (comportamiento del sistema) y no funcionales (restricciones y criterios de calidad). Esta clasificación permitirá, en capítulos posteriores, validar el grado de consecución de los objetivos planteados.

\subsection{Requisitos funcionales}
Los requisitos funcionales describen las acciones, funciones y comportamientos específicos que el sistema debe realizar para cumplir su propósito. Para el control de un péndulo invertido sobre carro se definen: 
\begin{itemize}
	\item \textbf{RF1. Modelado y simulación:} El sistema debe integrarse en un entorno simulación (Matlab/Simulink) para el desarrollo de algoritmos de control como paso previo a su implementación en hardware real. Se requiere el modelado de la dinámica no lineal y la introducción de los parámetros (masas, inercias, rozamientos...) que caracterizan el sistema real. 
	
	\item \textbf{RF2. Visualización y telemetría en ROS:} Se requiere establecer un puente de comunicación (ROS Toolbox) que publique el estado del sistema (\textit{joint states}) para su visualización en tiempo real mediante un modelo URDF en Rviz.  

	\item \textbf{RF3. Control de inyección de energía (Swing-up):} El control debe ser capaz de balancear el péndulo desde su posición estable ($q = \pi rad$) hasta su extremo opuesto ($ q = 0 rad$) mediante técnicas de inyección de energía. 
	
	\item \textbf{RF4. Control de estabilización (Realimentación del estado):} El sistema debe conmutar automáticamente a un control por realimentación del estado para mantener el péndulo en la vertical y posicionar el carro en un punto del riel. 
	
	\item \textbf{RF5. Adquisición de señales:} El firmware debe procesar las señales de los encoders en cuadratura y ejecutar la ley de control con una frecuencia de muestreo suficiente para garantizar la estabilidad del sistema inestable.  
	
\end{itemize}

\subsection{Requisitos no funcionales}
Los requisitos no funcionales, describen como debe comportarse el sistema y son esenciales para determinar su calidad. Para el caso en concreto: 

\begin{itemize}
	\item \textbf{RNF1. Determinismo y tiempo real estricto:} El bucle de control debe ejecutarse dentro de una rutina de interrupción (ISR) de prioridad máxima en la DSP, garantizando un periodo de muestreo constante y un \textit{jitter} despreciable.
	
	\item \textbf{RNF2. Robustez y márgenes de estabilidad:} El sistema debe ser capaz de rechazar perturbaciones externas moderadas y ser tolerante a las discrepancias producidas por las dinámicas no modeladas (fricciones no lineales y holguras mecánicas).
	
	\item \textbf{RNF3. Seguridad y gestión de fallos:} 
	\begin{itemize}
		\item \textit{Mecánica:} El software debe implementar una parada de emergencia si el carro excede los límites de seguridad del riel.
		\item \textit{Eléctrica:} Se debe asegurar el aislamiento galvánico mediante optoacopladores entre la etapa de potencia (24V) y la etapa de control (3.3V).
	\end{itemize}
	
	\item \textbf{RNF4. Abstracción de hardware (HAL):} Se debe emplear las librerías de bajo nivel ofrecidas por el fabircante de la DSP para asegurar su correcta programación, portabilidad y estandarización del código. 
	
\end{itemize}
